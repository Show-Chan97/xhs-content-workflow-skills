# 内容电商会议执行拆解

把会议里提到的方向、承诺、问题和进度，转成团队能够执行并在两周后逐条核验的作业纸。重点不是复述会议，而是明确谁做什么、何时完成、什么算交付，以及哪些变化会使原判断失效。

## 开始前

完整读取以下参考文件：

1. [evidence-and-input-rules.md](references/evidence-and-input-rules.md)：输入、证据标签和缺失信息处理。
2. [analysis-framework.md](references/analysis-framework.md)：优先级、执行画像、盲区和胜负手判断规则。
3. [output-spec.md](references/output-spec.md)：固定输出结构和交付检查。
4. [feishu-cli-policy.md](references/feishu-cli-policy.md)：飞书链接读取、写入、群消息、任务和回读的唯一执行方式。

## 工作流

### 1. 获取并界定输入

- 接受飞书妙记链接、其他会议记录链接、逐字稿、纪要或用户直接粘贴的会议文字。
- 飞书链接必须通过 `lark-cli` 获取正文；不得改用浏览器、连接器、通用飞书能力或直接 API。CLI 读取失败时说明实际原因，并请用户粘贴转写文本。不要假装已经读到链接内容。
- 记录品牌名、品类、当前阶段、会议日期、团队角色和已提供的数据口径。
- 缺少品牌、品类或阶段时继续完成候选版，但在报告头标为 `[待确认]`；缺少会议正文时停止分析，因为无法从零生成会议行动项。
- 默认只依据用户提供的会议材料和数据。仅在用户明确要求时补充外部资料，并把外部资料与会议证据分开标注。

### 2. 建立证据清单

- 从会议中提取决定、承诺、问题、进度、数据、负责人、时间和依赖关系。
- 为每条结论标注 `[会议明确]`、`[上下文推断]`、`[建议]` 或 `[待确认]`。
- 不补写会议没有指定的姓名、日期、预算、基线、目标值或行业事实。
- 将“已经决定的事项”和“建议新增的验证动作”分开。盲区建议不能伪装成会议已确定的待办。

### 3. 拆解可验证待办

- 把方向词改成原子动作。每条至少包含动作、交付物和验收证据；能从会议得到数量、阈值和日期时一并写明。
- 用二元判断检验每条待办：到复盘日能明确回答“完成”或“未完成”。不能判断时继续拆，或标记缺失标准。
- 按 [analysis-framework.md](references/analysis-framework.md) 的定义分为 P0、P1、P2。
- 把预算上限、冻结变量、通过线和止损阈值写进相关事项的执行约束，不要仅因它们重要就另建待办。只有会议明确要求独立交付或确实需要单独执行动作时，才拆成新行。
- 建议新增的测量、留痕或控制动作优先作为原事项的启动前置条件；不要用大量建议性 P0 扩大会议原有承诺范围。
- 负责人未明确时写 `⚠️ 未指定·待补充`；方向明确但动作不足时写 `⚠️ 方向已定·待拆动作`；只有进度没有下一步且无法可靠推断时写 `⚠️ 需下次会议确认`。
- 将待办表中所有 P0 且未指定负责人的真实行动项在报告最前面单独提醒。约束、阈值和待确认字段本身不计为一项；即使为 0 项，也明确写出 0 项。

### 4. 展开 P0/P1 执行画像

逐条回答：

1. 谁负责；若未指定，写需要哪类角色，不替老板点名。
2. 做成什么样算合格；缺少目标值时写清待补数据和确定标准的方法。
3. 什么证据代表已经交付；禁止使用“基本完成”“持续优化”等模糊状态。
4. 哪些外部、数据、人员变量会触发重新判断，以及触发后的具体动作。
5. 未做或未做成会引发什么连锁影响；只有输入支持时才量化金额、比例或天数。

### 5. 识别会议盲区

- 只选择会议中没有实质讨论、但会影响当前决策的 3–5 个问题。
- 使用 [analysis-framework.md](references/analysis-framework.md) 的盲区清单做对照，不要机械输出全部项目。
- 每个盲区写明关注理由、不处理的后果和一个低成本验证动作，包括建议角色、时间窗口、投入时间和交付物。
- 缺少支持证据时将盲区写成待验证假设，不把推测写成品牌现状。

### 6. 选择唯一胜负手

- 只输出一个胜负手：它的结果必须能改变其他多项决策的依据或顺序。
- 根据当前阶段、依赖关系、已有数据和学习价值筛选，不以“大家都觉得重要”作为理由。
- 写出胜负手、2–3 条依据、单一可验证的赢面指标、赌赢后的连锁动作、赌输后的时间/预算/机会成本止损线。
- 证据不足时仍只保留一个候选，但标题写 `暂定胜负手（待验证）`，并列出使其转正所缺的最少证据。

### 7. 生成两周复盘表

- 为待办表中的每一项建立对应复盘行，保留当时的负责人、优先级和验收标准。
- 将根因归入变量变化、执行不到位、判断失误或待进一步确认；不要把所有未完成都归结为态度问题。
- 要求每位负责人回答：是否做完、过程中发现了什么、下一轮继续/调整/放弃哪一种。

### 8. 完成交付检查

按 [output-spec.md](references/output-spec.md) 逐项检查：

- 五个主体段落全部存在；没有内容时写“暂无”，不要悄悄省略。
- P0 未认领提醒位于报告开头。
- 每条待办可二元验收，且 P0/P1 都有执行画像。
- 负责人、日期、数据目标和行业判断没有被编造。
- 建议动作没有自行补具体日历日期、预算、样本量、基线或目标值；输入缺失时使用依赖节点和“待确认”。
- 盲区为 3–5 个，且明确区分事实与假设。
- 胜负手只有一个，并同时包含赢面指标与止损线。
- 两周复盘表覆盖全部待办。
- 没有时间戳时，不虚构会议跑题所占百分比；改为定性说明“无法量化时间占比”。

## 外部写入边界

- 生成报告不等于发送。用户要求发到工作群、写入飞书文档或创建任务时，先展示最终内容并取得明确确认。
- 所有飞书发送、写入和任务创建只通过 `lark-cli` 执行；写入后仍通过 `lark-cli` 回读核验标题、五段结构、表格行数和链接。失败时报告实际状态，不声称已完成。
