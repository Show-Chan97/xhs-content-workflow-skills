# 会议复盘 Base 交付包规范

当用户要求把会议拆解结果生成飞书多维表、在 Base 中保存报告，或按行动分工表交付时，使用本规范。标准产物是同一个 Base 内的一张行动数据表和一篇会议执行报告文档；两者共享同一份结论，不重新生成两套内容。

## 一、默认产物

- 新 Base 名称：`{YYYY-MM-DD}-{品牌}-{会议主题}会议`，例如 `2026-07-22-绽家-内容策略复盘会议`。
- 初始数据表名称：`复盘行动分工`。
- Base 内文档名称：`{品牌或项目}-会议执行报告-{会议日期或待确认}`。
- 默认新建独立 Base，不修改参考样表或会议来源。用户明确指定已有 Base 时，才改为在指定 Base 中新建行动表和报告文档。
- 一条原子待办对应一条记录。约束、阈值、盲区和胜负手不单独成行；只有它们已经成为真实行动并具有交付物时才写成记录。
- 报告文档完整写入报告头、P0 未认领提醒、待确认清单和五个主体段落。报告中的待办数量、负责人、优先级和验收标准必须与行动表一致。

Base 命名规则：

1. 日期使用会议日期并统一为 `YYYY-MM-DD`，不能改用执行日期或建表日期。
2. 品牌使用会议材料或用户确认的正式品牌名。
3. `会议主题`使用会议标题中的具体主题，例如“内容策略复盘”“新品上市启动”；不能只写“项目”“复盘”等无法辨认的泛词。
4. 会议主题已经以“会议”结尾时不重复追加；否则在末尾追加“会议”。
5. 日期、品牌或会议主题任一缺失时，可以继续生成内容预览，但不得实际创建 Base。将缺失项列入待确认清单，补齐后重新展示最终名称并等待“确认执行”。

## 二、固定九字段

按下列顺序建字段。把 `核心问题` 作为主字段，便于在记录链接、通知和移动端列表中直接识别事项。

| 字段 | 类型 | 填写规则 |
|---|---|---|
| 核心问题 | text | 会议中需要解决的具体问题或决策阻塞；不能把“持续优化”等方向词当问题 |
| 板块 | select | 从本次会议归纳 3–8 个项目板块；同义项合并，不照搬其他品牌选项 |
| 解决方案 | text | 使用“动作；交付物；验收标准”的紧凑结构，必须能二元验收 |
| 优先级 | select | 只允许 `P0-紧急`、`P1-重要`、`P2-常规` |
| 负责人 | text | 会议明确的姓名或角色；未指定写 `待确认`，不替用户点名 |
| 协同人 | text | 只写会议明确的协同人或角色；未提及时留空 |
| 截止日期 | datetime | 只写已确认的具体日期；只有相对期限或未给日期时留空 |
| 状态 | select | 只允许 `待启动`、`进行中`、`已完成`、`暂停`；新拆事项默认 `待启动` |
| 备注 | text | 写证据标签、验收证据、约束、依赖和未换算的相对期限；没有内容时留空 |

`负责人` 与 `协同人` 默认使用文本字段，以保留姓名、职能和“待确认”。只有用户明确要求人员字段，且已通过飞书 CLI 解析出真实用户 ID 后，才改为 `user` 类型。

## 三、板块生成

先从会议材料和待办中归纳板块，再生成单选项：

1. 使用能代表业务责任域的短名称，例如“内容方向”“产品定位”“团队能力建设”“AI工具应用”“运营执行”。
2. 只有一条记录的细碎主题优先并入上位板块；不要为每条记录创建一个选项。
3. 不能从材料判断时使用“待归类”，不要复制参考样表中的品牌专属板块。
4. 预览时同时展示板块列表和每个板块的记录数，供用户确认。

## 四、内容映射

| 作业纸来源 | 多维表字段 |
|---|---|
| 待办背后的问题、阻塞或机会 | 核心问题 |
| 业务责任域 | 板块 |
| 具体动作、交付物、交付标准 | 解决方案 |
| P0 / P1 / P2 | P0-紧急 / P1-重要 / P2-常规 |
| 负责人 | 负责人 |
| 明确协作角色 | 协同人 |
| 已确认完成日期 | 截止日期 |
| 已知执行状态 | 状态；没有状态证据时为待启动 |
| 证据标签、验收证据、变量边界、依赖、相对期限 | 备注 |

记录排序为：未认领 P0、其他 P0、P1、P2；同级保持会议出现顺序。`[建议]` 行可以进入预览，但备注必须保留 `[建议]`，不得伪装成会议已决定事项。

## 五、报告文档内容

报告文档使用 [output-spec.md](output-spec.md) 的完整五段式作业纸，不把聊天摘要或九字段表格预览冒充报告。文档固定包含：

1. 报告标题、会议日期、当前阶段、材料来源和证据说明；
2. P0 未认领提醒与待确认清单；
3. 待办事项拆解；
4. P0/P1 执行画像；
5. 会议盲区；
6. 唯一胜负手及止损线；
7. 两周后复盘预备表。

默认使用结构清楚、组件克制的飞书文档样式：正文使用连贯段落，真实行列数据使用表格，任务清单按需使用待办项；P0 未认领可使用一个警示高亮块。不要把每个字段升成标题，也不要重复显示文档标题。

## 六、写入前预览与确认

先输出：

1. 按“日期-品牌-会议主题会议”生成的新 Base 名称、数据表名称、报告文档名称和目标文件夹；
2. 九个字段的类型与单选项；
3. 预计写入行数、板块分布、负责人待确认数、日期空缺数；
4. 与第一段待办一一对应的九列表格预览；
5. 将写入报告文档的完整五段式报告预览；
6. 明确说明参考 Base 不会被修改，行动表和报告文档将新建在同一个 Base 内。

用户只要求预览时，交付行动表与报告预览后停止。用户要求实际创建飞书多维表或完整交付包时，展示上述变更清单并等待明确回复“确认执行”。一次确认同时覆盖新 Base、行动表、记录和报告文档；任何名称、字段、选项、目标位置、记录或报告正文发生变化，都要更新预览并重新确认。

## 七、通过飞书 CLI 创建

完整读取 `feishu-cli-policy.md`、`lark-shared`、`lark-base`、`lark-doc` 及对应的字段、批量写入、文档 XML、文档样式、更新和读取指南后执行：

1. 使用 `lark-cli auth status --json --verify` 验证用户身份与授权。
2. 通过 `lark-cli base +base-create --as user` 一次创建新 Base、`复盘行动分工` 初始表和九字段 schema。`板块`使用本次确认的动态选项；优先级和状态使用固定选项。
3. 从成功响应获取真实 `base_token` 和 `table_id`，不得猜测。
4. 通过 `lark-cli base +field-list --as user` 回读字段，核对名称、类型和选项后再写记录。
5. 通过 `lark-cli base +record-batch-create --as user` 批量写入；字段顺序必须与行值严格一致，空日期和空协同人传 `null`，单批不超过 200 行。
6. 通过 `lark-cli base +base-block-create --base-token <真实 token> --type docx --name <报告文档名称> --as user` 在同一个 Base 根目录新建报告文档。获取真实 `docx_token`；创建响应未返回时，用 `lark-cli base +base-block-list --type docx --as user` 按本次唯一名称解析，不得猜 token。
7. 报告文档是本次新建的空文档时，通过 `lark-cli docs +update --doc <docx_token> --command overwrite --content <完整 XML> --as user` 写入完整报告。恢复执行时先读取现有文档；已有内容时不得盲目覆盖。
8. 通过 `lark-cli base +base-block-list --as user` 核对行动表和报告文档都属于该 Base；通过记录读取核对本次全部记录；通过 `lark-cli docs +fetch --doc <docx_token> --detail simple --as user` 回读完整报告。
9. 核对报告标题、五段结构、待办数量、P0 数量、负责人和验收标准与行动表一致。只有所有命令退出码为 0、`ok == true`，且表与文档分别回读一致时才标记完成。

建议的字段 JSON 形状：

```json
[
  {"name":"核心问题","type":"text"},
  {"name":"板块","type":"select","multiple":false,"options":[{"name":"按本次会议确认的板块"}]},
  {"name":"解决方案","type":"text"},
  {"name":"优先级","type":"select","multiple":false,"options":[{"name":"P0-紧急","hue":"Red","lightness":"Light"},{"name":"P1-重要","hue":"Orange","lightness":"Light"},{"name":"P2-常规","hue":"Gray","lightness":"Lighter"}]},
  {"name":"负责人","type":"text"},
  {"name":"协同人","type":"text"},
  {"name":"截止日期","type":"datetime","style":{"format":"yyyy-MM-dd"}},
  {"name":"状态","type":"select","multiple":false,"options":[{"name":"待启动","hue":"Gray","lightness":"Lighter"},{"name":"进行中","hue":"Blue","lightness":"Light"},{"name":"已完成","hue":"Green","lightness":"Light"},{"name":"暂停","hue":"Orange","lightness":"Light"}]},
  {"name":"备注","type":"text"}
]
```

该 JSON 是字段形状模板；执行前必须把板块占位选项替换为本次已确认的真实选项。

## 八、断点恢复与失败处理

- 缺少 CLI、授权或权限：保留九列表格预览并报告实际阻塞，不切换浏览器或其他接口。
- 每完成一步就保留当前 `base_token`、`table_id`、已创建记录 ID、文档 block ID 和 `docx_token`。恢复时先回读这些真实对象，只补尚未完成的部分。
- 建表成功但写记录失败：报告已创建的 Base 链接、成功与失败行数，不重复建 Base。
- 行动表完成但文档创建或写入失败：保留现有 Base 和行动表，只重试文档步骤，不重复写记录。
- 文档已创建但正文未写完：先通过 `lark-cli docs +fetch` 判断实际内容，再补写或定向修正；不得再次创建同名文档。
- 表或文档写入成功但回读失败：写“已提交但未完成复核”，不得标记完成。
- 字段或选项与确认稿不一致：停止写记录，先修正方案并重新确认；不得向错误 schema 强行写入。
- 只有 Base、九字段行动表、全部记录和报告文档四部分都存在且回读一致，才报告完整交付。
